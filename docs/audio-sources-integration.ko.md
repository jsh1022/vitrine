# WireGuard · 무손실 애드온 · 상세 재생 정보

**후속 수정:** 버튼의 화면 표시 누락을 고치고 WireGuard를 독립된 앱 URLSession 프록시로
확장했습니다. 최신 메뉴·사용 순서·적용 범위는 [독립 프록시 안내](wireguard-proxy.ko.md)를
따릅니다. 아래 애드온 전용 WireGuard 설명은 첫 통합의 동작이며, 새 앱 프록시 모드를
켜면 애드온 스위치와 무관하게 앱 URLSession 요청에 적용됩니다.

이 수정본은 Vitrine `2f1f1580bb681c5856ee31467092eae423373fee`에 적용한 실험적 통합입니다.
완성된 IPA나 실기기 검증을 마친 배포판은 아닙니다.

재설계 플레이어의 애드온 재생 방식, 음질 정보의 측정 범위, 이전·현재·다음 곡 화면의 동작과 검증 상태는 [재생 모드 안내](redesigned-playback-modes.ko.md)를 참고하세요.

## 정렬 대기 단축

기존 동기화 방식을 유지하며 원래 Spotify PCM의 최근 연속 구간을 보관합니다. 파일을 받는 동안
실제로 재생된 소리가 있으면 이를 재사용하고, 부족한 부분만 더 수집합니다. 비교에는 기존처럼
첫 정렬에는 연속 3초와 정규화 상관계수 0.8 이상이 필요합니다. 곡·탐색·재생 상태·출력 경로가 바뀌어 source epoch가
달라지거나 오디오가 끊기면 이전 구간을 이어 붙이지 않습니다. Spotify가 일시정지된 대기 모드나
출력 레이트 변경 직후에는 수집 시간을 그대로 기다릴 수 있습니다.

같은 곡·같은 파일에서 3초 정렬의 상관계수가 0.98 이상이면 녹음의 위치 관계를 보관합니다.
일시정지·재개나 탐색 후에는 이전 출력 카운터를 그대로 쓰지 않고, 새 epoch의 원래 Spotify 소리
1초로 예상 위치 주변을 확인합니다. 전체 상관계수 0.98 이상, 분리된 후보와의 점수 차이 0.025 이상,
네 구간 각각 0.96 이상과 게인 일관성 조건을 모두 통과해야 새 출력 카운터에 연결합니다.
위치 보고는 검색 힌트로만 씁니다. 확인 실패 시 기존 3초 정렬로 돌아가며, 곡 변경·건너뛰기·정지·
출력 경로 변경·Karaoke 변경·파일 교체 시 보관한 관계를 폐기합니다. 출력 레이트가 달라도 재사용하지
않습니다. 실기기의 재개 지연과 반복 구간·원격 탐색 동작은 별도 확인 대상입니다.

파일은 위치 힌트 주변 ±2초부터 디코딩·비교합니다. 비교 길이 3초를 포함해 앞 2초~뒤 5초를
디코딩합니다. 불일치하면 기존 ±8초 범위로 확장한 뒤, 다시 불일치하면 완성된 파일은 전체
검색으로, 다운로드 중인 FLAC은 힌트 주변 ±32초까지 확장합니다. 힌트는 검색 범위에만 사용하고
실제 전환 위치는 소리 비교 결과로 정합니다. 사전 준비 3곡 정책은 유지하고, 완전히 받은 바로 다음
곡은 앞부분 최대 20초의 검색용 디코딩까지 준비합니다. 실제 레이트가 달라지면 캐시를 사용하지
않습니다. 곡이 넘어와도 실제 소리 검증은 생략하지 않습니다.

격리된 iOS 테스트는 실제 정렬 엔진으로 같은 녹음의 위치·게인, 3초 수집분 재사용, 다음 파일의 사전
디코딩 사용, source epoch 변경 시 이전 소리 폐기, 일시정지·앞뒤 탐색 후 새 카운터에 연결,
곡 식별자 변경·정렬 폐기 시 전체 검증 복귀, 다른 녹음 거부를 확인합니다. 실제 애드온 서버와
기기에서 줄어드는 대기 시간은 별도 확인 대상입니다.

곡 변경 시 새 현재 곡과 URI가 같은 진행 중 사전 준비 작업은 취소하지 않고 이어갑니다.
완료 결과를 현재 곡 요청에 넘기며, 해당 작업 뒤의 이전 사전 준비 계획은 중단합니다.
전체 파일 요청은 같은 HTTP 작업을 이어가며, 직접 FLAC은 현재 곡 자동 전환이 허용되고 기존
부분 파일 검증을 통과하면 다운로드 도중에도 인계합니다. 2MiB 앞부분 요청은 그 요청 완료 후
기존 URL·강한 ETag·Range 검증을 거쳐 나머지를 이어받습니다. 서버가 Range를 무시하거나
ETag가 달라지면 기존처럼 처음부터 받습니다. 다른 곡으로 변경·정지·설정 변경 시 기존 취소 정책을 유지합니다.
건너뛰기 명령의 대상이 아직 보고되지 않았을 때는 최대 2초만 후보를 보존합니다.
3초 비교는 실험적 변경이며 실제 음악의 반복·무음 구간 오정렬률과 체감 시간은 실기기 검증이 필요합니다.

## 추가한 기능

- **HTTP 음원 애드온**: 생성된 HTTPS 루트/manifest URL을 추가하고 연결 검사·삭제·현재 곡 재시도를 합니다. 최대 8개 소스를 추가 순서대로 조회합니다. 공급자 코드는 실행하지 않습니다.
- **앱 내부 WireGuard**: 첨부 BitChord의 Go 엔진을 Vitrine 전용 URLSession에 연결했습니다. `.conf`를 파일 앱에서 가져오고 Keychain에 저장합니다. 애드온 JSON과 음원 요청에만 적용됩니다. Spotify 로그인·Spotify 스트림·다른 앱의 트래픽을 터널링하지 않습니다.
- **상세 재생 정보**: 곡·아티스트·URI·재생 위치·상태, 준비된 파일의 FLAC/ALAC 또는 무압축 PCM WAV/AIFF 형식·원본 샘플레이트·비트 깊이·채널·평균 파일 비트레이트, 실제 클라이언트 PCM·오디오 세션 레이트·출력 경로·출력 지연·속도·피치·Karaoke·터널 상태를 표시합니다.
- 기본 UI와 재설계 UI 모두 Player 설정에서 열 수 있습니다. 플레이어의 `⋯`에도 Playback details 진입점을 추가했습니다.

## 빌드

Mac에서는 기존 README의 Xcode 26 이상·Theos·IPA 주입 도구를 설치하고, 추가로 `vendor/wireguard/go.mod`에 맞는 Go를 설치합니다. Go 1.27.4로 검사했습니다.

```sh
make release IPA=/path/to/your/decrypted-spotify.ipa
```

WireGuard는 기본 포함됩니다. 제외하려면 `make release WIREGUARD=0 IPA=...`를 사용합니다.
제외 빌드에서 WireGuard 설정을 켜면 애드온 요청을 차단합니다. 직접 연결로 조용히 우회하지 않습니다.

Mac 없이 빌드하려면 본인 GitHub 포크에 수정 소스를 반영한 후 기존 **Build IPA from your own Spotify IPA** 워크플로를 실행합니다. Go 설치 단계를 추가했습니다. 실제 Actions 실행이나 GitHub 업로드는 이 작업에서 수행하지 않았습니다.

Spotify 9.1.78/9.1.88/9.1.90의 본인 decrypted IPA가 필요하며, 결과 IPA에는 본인 인증서로 서명해야 합니다. 기존 UI 재설계는 iOS 26 이상을 권장합니다. WireGuard를 애드온 URLSession에 적용하는 기능은 iOS 17 이상이 필요합니다.

## 설정 순서

1. `Settings → Mod Settings → Player → Lossless files`를 켜고 Spotify를 한 번 다시 실행합니다. 오디오 훅은 시작할 때 설치됩니다.
2. `Lossless sources & WireGuard → Add source`에서 본인이 사용할 수 있는 애드온의 생성된 HTTPS 링크를 붙여넣습니다. GitHub 저장소 링크나 HTML 설정 페이지는 사용할 수 없습니다.
3. 소스 항목에서 `Test manifest`를 실행합니다. 이 검사는 manifest 계약과 연결만 검사하며, 해당 곡의 매칭이나 실제 재생 성공까지 보장하지 않습니다.
4. `HTTP lossless addons`를 켭니다. 기본값은 휴대전화 데이터 다운로드 차단이며, 필요하면 `Allow cellular downloads`를 켭니다.
5. 터널을 쓰려면 `Import .conf file`로 본인 WireGuard 구성을 가져온 다음 `WireGuard for addons`를 켭니다. 설정을 변경하면 새 준비 시도가 현재 곡을 다시 조회합니다. 실제 peer 핸드셰이크는 첫 터널 요청 이후 확인합니다.
6. `Playback details`에서 준비된 파일 형식과 출력 상태를 확인합니다. `External lossless frames reaching local output`은 최근 0.5초 동안 외부 PCM 프레임이 로컬 출력 경로에 전달된 경우에만 표시합니다. 정렬만 된 상태는 따로 표시합니다.

프로필을 교체하려면 WireGuard를 끄고 Spotify를 다시 실행한 뒤 가져옵니다. 저장된 프로필을 삭제해도 실행 중인 Go 엔진은 프로세스가 종료될 때 메모리에서 해제됩니다. 터널을 끈 뒤 재실행하면 사용 중인 엔진도 종료됩니다.

## 지원 범위와 동작

`/manifest.json`, `/search?q=...`, `/stream/{id}` 계약을 사용합니다. 검색 결과의 직접 `streamURL`도 지원합니다. 비밀 경로 접두사와 기본 URL의 query를 보존하고, 곡 ID를 한 개의 경로 세그먼트로 인코딩합니다. BitChord iOS proxy.28과 같은 `User-Agent: BitChord/v1.8`을 보내며 API의 `Accept`는 `application/json`입니다. `bitchordAuth: true` 선언만으로 사전 차단하지 않고 제공받은 URL로 실제 요청합니다. 이 헤더는 공식 앱 증명이 아니며 인증 토큰이나 증명을 생성하지 않습니다. 서버의 401/403 거부는 그대로 실패 처리하므로 공식 앱 증명을 필수로 요구하는 서비스는 사용할 수 없습니다.

지원 대상은 **HTTPS 정적 VOD**입니다. 직접 파일은 완성된 스테레오 FLAC/ALAC 또는 무압축 PCM WAV/AIFF를 받습니다. HLS는 master/media playlist에서 fMP4 `EXT-X-MAP` 또는 단일 직접 세그먼트만, DASH는 단일 Period의 SegmentBase/full file, SegmentList 또는 SegmentTemplate의 duration/Timeline을 최대 2048개 세그먼트까지 지원합니다. 암호화·DRM·라이브·discontinuity·Atmos·MP3/AAC는 지원하지 않습니다. 추가 요청 헤더가 필요한 서버·ISRC 전용 조회·공급자별 사용자 설정 폼도 지원하지 않습니다. 호스팅된 상용 공급자와의 실시간 호환성을 확인하지 않았으며 기본 서버 주소나 계정을 넣지 않았습니다.

제목과 아티스트를 보수적으로 대조하고 길이 차이가 2초 이내인 후보 한 개를 선택합니다. live/remaster 등의 표기는 지우지 않습니다. 동일 곡을 놓칠 수 있으며, 성공한 metadata 매칭도 동일 마스터를 증명하지 않습니다. 전경의 직접 FLAC은 서버가 알려준 전체 크기가 128 MiB 이하이고 바이트가 끊김 없이 이어지며 FLAC 메타데이터가 완전하고, native decoder에서 코덱·스테레오·샘플레이트·비트 깊이·길이를 확인한 경우 다운로드 도중 준비를 게시할 수 있습니다. native parser가 아직 자라는 파일을 열지 못하면 전체 다운로드 후 처리합니다. 디코드에 필요한 앞부분과 정렬 검색 구간을 준비하고, worker에서 새 바이트를 기다립니다. render ring에 프레임이 부족하면 Spotify 오디오를 유지합니다. 게시 시에도 기존 Spotify 오디오와 약 3초 상관 분석을 거쳐야 교체되며, 초기 대기 설정은 이 조기 전환이 수락되면 끝납니다. 나머지 전송은 최대 120초로 제한하고 전송 실패 시 외부 재생을 취소합니다. 이 점진적 경로는 전경 직접 FLAC에만 해당합니다. FLAC 이외의 직접 파일과 HLS/DASH는 128 MiB 이하 전체 다운로드 후 준비합니다. 세그먼트 스트림은 로컬 AVAssetReader로 변환하며, 측정된 16/24/32-bit 정수 깊이를 원래 샘플레이트로 WAV 출력합니다. 깊이를 알 수 없거나 타임라인에 빈 구간이 있으면 거부합니다. 0이 아닌 DASH presentationTimeOffset은 타임라인 보정이 구현되지 않아 거부합니다. 준비 또는 정렬에 실패하면 Spotify 오디오를 계속 사용합니다.

애드온 JSON은 요청당 1 MiB·20초, 음원은 128 MiB·120초로 제한합니다. 서버가 429 또는 5xx 응답과 함께 유효한 `Retry-After`를 보내면 해당 대기 시간만 따릅니다. 자체 지수형 대기와 429의 기본 60초 대기는 적용하지 않습니다. 헤더가 없거나 유효하지 않으면 해당 요청은 실패 처리하며 자동 반복 재시도를 예약하지 않습니다. 연결 실패·시간 초과도 해당 시도만 종료하고 소스 전체에 별도 대기를 걸지 않습니다. 중복 검색·stream 조회를 줄이기 위해 JSON 응답을 제한된 크기와 짧은 수명의 캐시에 보관합니다. 포그라운드 점진 FLAC의 나머지 다운로드는 조기 전환 수락 뒤에도 최대 120초 동안 이어집니다. 포그라운드 재생 준비가 대기 중이면 백그라운드 파일 수신을 중단하고 100ms 간격으로 확인하며, 현재 곡 준비가 끝난 뒤 사전 준비를 재개합니다. 사전 준비는 Spotify의 전체 대기열에서 다음 최대 3곡을 대상으로 합니다. 바로 다음 곡은 네트워크 설정에 따라 전체를 받고 나머지 2곡은 앞부분 최대 2 MiB씩 순차 준비합니다. 더 먼 곡의 준비는 500ms씩 간격을 두며 현재 곡 준비가 우선합니다. 접두부만 받는 사전 준비는 세그먼트 스트림을 건너뜁니다. 전체 파일 준비에는 Wi-Fi 또는 전체 셀룰러 다운로드 허용이 필요합니다. 셀룰러 차단은 요청 전 네트워크 확인·URLSession 설정·전송 중 경로 감시로 적용합니다. 새 곡과 설정 변경은 기존 전송 경로를 사용해 진행 중 준비를 취소하고 이전 세대의 응답을 버립니다. 준비 파일은 임시 폴더에 두고 곡 전환 또는 다음 실행의 첫 준비 때 정리합니다.

Spotify는 큐·컨트롤·가사 타이밍을 계속 담당하고 자체 스트림도 내려받습니다. 정상 속도 1×와 Karaoke가 꺼진 상태에서 기존 엔진의 정렬 조건을 만족해야 외부 파일로 전환됩니다. Spotify Connect의 원격 기기 오디오는 개선하지 않습니다. 원본 고해상도 파일이 클라이언트 레이트로 리샘플링될 수 있으며, Bluetooth 등 출력 경로까지 bit-perfect라고 주장하지 않습니다. Spotify 자체 디코더의 코덱·비트레이트는 검증된 API에서 얻을 수 없어 미확인으로 표시합니다. 알아내지 못한 원본 bit depth를 Float32 출력으로 추정하지 않습니다.

## 보관과 라이선스

비밀 링크 및 WireGuard 프로필은 기기 전용 Keychain에 보관합니다. 환경설정 내보내기에 포함하지 않습니다. 애드온 API 리다이렉트는 거부하고, 음원 리다이렉트는 HTTPS만 허용합니다. 원격 오류 본문이나 URL을 로그/상태에 노출하지 않습니다. WireGuard 엔드포인트가 hostname이면 최초 연결을 위한 DNS 조회는 터널 밖에서 한 번 수행됩니다.

첨부 `BitChord-iOS-main.zip`의 `WireGuard/`를 GPL-3.0에 따라 포함했고 기존 제3자 라이선스를 유지했습니다. 엔진 출처와 ZIP SHA-256은 `vendor/wireguard/README.vitrine.md`에 있습니다. 애드온 JSON 모델은 참고하고 Vitrine의 Objective-C 클라이언트로 새로 구현했습니다. IPA 파이프라인은 WireGuard의 GPL 및 제3자 고지도 앱에 넣습니다.

## 수행한 검증

- Go 1.27.4에서 `go test ./...`와 `go test -race ./...` 통과. 로컬 WireGuard peer를 사용한 핸드셰이크·터널 DNS·HTTPS·Range·인증 거부·직접 연결 차단·소켓 재생성·키 정보 비노출 검사가 포함됩니다.
- Linux에서 iPhoneOS 16.5 SDK와 Clang 19를 사용해 iOS arm64용 Go C archive 빌드 성공.
- 새 Objective-C 소스와 변경한 오디오 엔진·설정 페이지·플레이어 메뉴를 iOS arm64 타깃으로 컴파일 검사. WireGuard 포함/제외 양쪽 검사.
- Vitrine 레이어 검사·패치 공백 검사·셸 문법 검사·워크플로 YAML 파싱 수행.

**아직 실행하지 않은 검증**: Foundation 프로토콜 fixture 실행(`bash harness/audio-sources/check.sh`의 Mac 실행 파일), 실제 URLSession과 SOCKS5의 iPhone 통합, 실제 애드온 서버에서의 음원 준비, Spotify 기기 재생·전환·탐색·백그라운드·UI 레이아웃, 전체 Theos 링크·서명·IPA 설치. 기존 오디오 handoff harness는 Linux에 `xcrun`이 없어 실행할 수 없었습니다. `Audio sources checks` 워크플로에 Mac fixture와 iOS 소스 검사를 추가했으며, 전체 오디오 동작 검증은 기존 handoff harness와 실기기에서 진행해야 합니다.
